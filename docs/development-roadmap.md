# מפת הפיתוח של Featurn

תוכנית מוצעת להפיכת המערכת הקיימת מממשק ניהול ראשוני למוצר SaaS רב־עסקי
שניתן למכור, לתפעל ולהרחיב.

> הערכות הזמן הן סדרי גודל בלבד. הן תלויות בהחלטות המוצר, בחיבורי הספקים
> ובמצב סביבת Supabase.

## מה כבר קיים[h](http://127.0.0.1:5174/)

- אימות משתמשים באמצעות דוא״ל וסיסמה או Google.
- תמיכה במספר עסקים באמצעות `business_members`.
- RLS פעיל בסביבת Supabase.
- יצירה ועריכה של לקוחות ותורים.
- יומן תורים המבוסס על FullCalendar.
- הגדרות בסיסיות לעסק ולשירותים.
- ארכיטקטורת `features` ו־`shared`.
- טיפוסי TypeScript שנוצרו מסכמת Supabase.
- עיצוב RTL אחיד ורספונסיבי.

## נקודת ההתחלה המומלצת

יש להתחיל בשלב 0. רוב שינויי Supabase נוצרו עד עכשיו ידנית ורק מיגרציית
סנכרון ה־sequences נמצאת בריפו. ללא סכמת מסד מלאה, RLS ו־RPCs במיגרציות,
אי אפשר לשחזר או לבדוק בבטחה סביבת ייצור.

---



## שלב 0 — בסיס שחזור וייצור

**תוצאה:** כל סביבת Supabase ניתנת להקמה מחדש מקוד בלבד, עם בדיקות
אוטומטיות.

**עדיפות:** חובה לפני פיצ'רים נוספים  
**הערכה:** 3–5 ימי עבודה

### מה נבנה

1. שחזור כל הטבלאות, RLS, policies, functions, triggers והאילוצים
  למיגרציות.
2. הוספת `supabase/config.toml` וסביבת Supabase מקומית שניתנת לאיפוס מלא.
3. הקשחת `create_business` כפעולה אטומית עם `SECURITY DEFINER` ו־
  `search_path` מפורש.
4. הוספת `.env` ל־`.gitignore`, יצירת `.env.example` ובדיקת היסטוריית Git
  לסודות.
5. יצירת seed מצומצם לפיתוח ולבדיקות, ללא מידע אמיתי.
6. הוספת CI שמריץ build, lint ובדיקות בכל שינוי.
7. הגדרת סביבות Development, Staging ו־Production.
8. הוספת בדיקת `npm audit` ותוכנית שדרוג תלויות מבוקרת.



### תנאי סיום

- פרויקט Supabase חדש עולה מהמיגרציות ללא פעולות ידניות.
- RLS מבודד שני עסקים ומוכיח הרשאות שונות ל־viewer, staff, admin ו־owner.
- Pull Request לא יכול לעבור כאשר build, lint או test נכשלים.
- `git check-ignore` מאשר שקובצי סביבה אמיתיים אינם ניתנים להוספה בטעות.

## שלב 1 — ליבת ניהול התורים

**תוצאה:** מנהל עסק יכול להגדיר שירותים וזמינות ולנהל מחזור חיים מלא של
תור.

**עדיפות:** MVP  
**הערכה:** 7–10 ימי עבודה

### מה נבנה

1. חסימת יצירת תור כאשר לעסק אין לקוחות והצעת מעבר ליצירת לקוח.
2. איפוס בחירת תור ומודלים פתוחים בהחלפת עסק פעיל.
3. CRUD מלא לשירותים: יצירה, עריכה, השבתה, משך, מחיר, זמן חיץ וצבע.
4. מסך שעות פעילות, ימי חופשה וחריגים לפי אזור הזמן של העסק.
5. בחירת שירות ביצירת תור וחישוב אוטומטי של שעת הסיום והמחיר.
6. הזזה, ביטול, השלמה וסימון אי־הגעה עם סיבת שינוי.
7. מניעת התנגשות אטומית במסד והצגת חלופות פנויות.
8. סינון היומן לפי שירות, סטטוס וטווח תאריכים.
9. הוספת URL לכל מסך כדי שרענון ודיפ־לינק ישמרו את המסך הנוכחי.



### תנאי סיום

- אי אפשר ליצור שני תורים חופפים גם בשתי בקשות מקבילות.
- תור חדש מכבד שעות פעילות, חופשות, משך שירות וזמן חיץ.
- כל פעולה ביומן מעדכנת את המסך ללא רענון ידני.
- החלפת עסק אינה משאירה מידע מהעסק הקודם.

## שלב 2 — צוות, משאבים והרשאות

**תוצאה:** המערכת תומכת בעסק עם מספר עובדים, תפקידים ולוחות זמנים נפרדים.

**עדיפות:** נדרש לפני מכירה לעסקים עם צוות  
**הערכה:** 7–12 ימי עבודה

### מה נבנה

1. ניהול חברי עסק: הזמנה, ביטול הזמנה, השעיה ושינוי תפקיד.
2. הוספת נותני שירות ומשאבים כגון חדרים או עמדות.
3. שיוך שירותים לעובדים והגדרת שעות פעילות אישיות.
4. יומן לפי עובד ותצוגה מאוחדת של העסק.
5. הסתרת פעולות ב־UI לפי תפקיד, בנוסף לאכיפת RLS.
6. Audit log לפעולות רגישות ולשינויי הרשאות.



### תנאי סיום

- עובד רואה ומבצע רק פעולות שמתאימות לתפקידו.
- זמינות מחושבת לפי העסק, העובד והמשאב.
- כל שינוי הרשאה מתועד עם המבצע והזמן.

## שלב 3 — לקוחות ו־CRM בסיסי

**תוצאה:** כרטיס לקוח מרכז מידע, היסטוריית תורים והעדפות תקשורת.

**עדיפות:** MVP משופר  
**הערכה:** 5–8 ימי עבודה

### מה נבנה

1. חיפוש, סינון, מיון ועימוד שרת בטבלת הלקוחות.
2. עמוד לקוח עם היסטוריית תורים, ביטולים, הערות ופעילות אחרונה.
3. מיזוג כפילויות ונרמול טלפון, דוא״ל ותעודה מזהה.
4. מחיקה רכה או אנונימיזציה במקום מחיקה מסוכנת.
5. ייבוא וייצוא CSV עם אימות, תצוגה מקדימה ודוח שגיאות.
6. שמירת הסכמות והעדפות SMS/WhatsApp עם תאריך ומקור.



### תנאי סיום

- הטבלה נשארת מהירה גם בעשרות אלפי לקוחות.
- פורמטים שונים של אותו מספר אינם יוצרים כפילויות.
- היסטוריית הלקוח זמינה ממסך אחד.

---



## שלב 4 — WhatsApp, קול והתראות

**תוצאה:** ערוצי התקשורת יוצרים ומעדכנים תורים דרך backend מאובטח.

**עדיפות:** לאחר שליבת הזמינות יציבה  
**הערכה:** 10–15 ימי עבודה

### מה נבנה

1. Edge Functions או backend לקליטת webhooks.
2. WhatsApp לאישור, תזכורת, שינוי וביטול תורים.
3. Vapi או סוכן קולי המשתמש באותה שכבת זמינות.
4. תבניות הודעה לפי עסק ושפה עם תצוגה מקדימה.
5. תור משימות עם retries, idempotency ו־dead-letter.
6. לוג תקשורת בכרטיס הלקוח ומדדי מסירה.



### תנאי סיום

- Webhook כפול אינו יוצר תור כפול.
- כשל זמני אצל ספק נשלח מחדש.
- סודות ספק זמינים רק בצד השרת.

---



## שלב 5 — קביעת תור עצמאית

**תוצאה:** לקוח יכול למצוא זמן פנוי ולקבוע, לשנות או לבטל תור ללא מנהל.

**עדיפות:** ערוץ צמיחה  
**הערכה:** 8–12 ימי עבודה

### מה נבנה

1. עמוד ציבורי ממותג לבחירת שירות, עובד ומועד.
2. אימות טלפון או קישור חתום לניהול תור.
3. הגבלות זמן להזמנה ומדיניות ביטול.
4. רשימת המתנה והצעת מקום שהתפנה.
5. Rate limiting, captcha לפי צורך ומניעת abuse.
6. זרימה נגישה המותאמת קודם כול למובייל.



### תנאי סיום

- הזמינות הציבורית זהה לזמינות המנהל.
- לקוח אינו יכול לגשת לתור של לקוח אחר.
- אפשר להשלים את התהליך במובייל ובמקלדת.

## שלב 6 — מוצר SaaS מסחרי

**תוצאה:** אפשר לצרף עסקים, לחייב אותם ולתמוך בהם תפעולית.

**עדיפות:** לפני מכירה רחבה  
**הערכה:** 10–15 ימי עבודה

### מה נבנה

1. תוכניות, תקופת ניסיון, מגבלות שימוש, מנוי וחשבוניות.
2. Onboarding מלא עם wizard ו־checklist להפעלה.
3. מסך ניהול פנימי לתמיכה עם הרשאות מבוקרות.
4. מדדי שימוש: תורים, ביטולים, no-show, תפוסה ומקורות הזמנה.
5. הקפאה, חידוש, ייצוא נתונים וסגירת עסק.
6. תנאי שימוש, פרטיות ומדיניות שמירת מידע לפי ייעוץ משפטי.



### תנאי סיום

- מצב המנוי נאכף בצד השרת.
- אפשר לטפל בתקלה של עסק בלי גישה לסודותיו.
- לכל עסק יש תהליך ייצוא וסגירת חשבון.

---



## שלב 7 — איכות, ניטור ושחרור

**תוצאה:** המערכת ניתנת לפריסה בטוחה, למדידה ולשחזור מתקלות.

**עדיפות:** מתמשך; שער חובה לפני Production  
**הערכה:** 5–10 ימי בסיס ולאחר מכן עבודה מתמשכת

### מה נבנה

1. בדיקות רכיבים והוקים, integration מול Supabase מקומי ו־E2E.
2. Modal משותף עם focus trap, סגירה ב־Escape, החזרת פוקוס ו־ARIA.
3. Error Boundary גלובלי עם מסך התאוששות.
4. דיווח שגיאות, structured logs ו־correlation IDs.
5. מדדי latency, כשלים, webhooks ותורים והתראות תפעוליות.

גיבויים, בדיקת שחזור, retention ו־runbook לת[http://127.0.0.1:5174/http://127.0.0.1:5174/](http://127.0.0.1:5174/)

קריות.

1. Code splitting, דחיסת הלוגו, ביצועי טבלאות ותקציב bundle.
2. בדיקות נגישות, דפדפנים ומובייל.
3. תיעוד ארכיטקטורה, setup, release ושינויי סכמה.



### תנאי סיום

- כניסה, יצירת לקוח, יצירת תור וביטול עוברים E2E.
- המודלים, הניווט והטפסים עוברים בדיקת axe.
- קיימת התרעה על כשל משמעותי לפני שלקוח מדווח.
- בוצעה והוכחה בדיקת שחזור מגיבוי.

## הצגה ושמירה כ־PDF



### אפשרות מומלצת — דרך Cursor והדפדפן

1. פתח את `docs/development-roadmap.md` ב־Cursor.
2. פתח Markdown Preview באמצעות `Ctrl+Shift+V`.
3. בתצוגה המקדימה פתח את תפריט האפשרויות ובחר לפתוח בדפדפן, או פתח את הקובץ
  מתוך GitHub לאחר העלאתו.
4. בדפדפן לחץ `Ctrl+P`.
5. בחר במדפסת **Save as PDF** או **Microsoft Print to PDF**.
6. בחר גודל A4 ושמור בשם `featurn-development-roadmap.pdf`.



### אפשרות נוספת — הרחבת Markdown PDF

1. התקן ב־Cursor את ההרחבה `Markdown PDF`.
2. פתח את קובץ ה־Markdown.
3. לחץ `Ctrl+Shift+P`.
4. הפעל `Markdown PDF: Export (pdf)`.

ה־PDF ייווצר ליד קובץ ה־Markdown. מומלץ לבדוק שהעברית מיושרת לימין לפני
שיתוף המסמך.
